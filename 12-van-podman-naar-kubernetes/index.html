12 Van Podman naar Kubernetes¶

12.1 Doelstellingen¶

Na dit hoofdstuk beheerst de student het volgende:

  • uitleggen wat podman kube generate doet en waarin het verschilt van een manifest dat je zelf schrijft;

  • van een bestaande Podman-pod een Kubernetes-manifest maken;

  • in zo'n gegenereerd manifest de regels herkennen die Kubernetes niet aanvaardt, en ze aanpassen;

  • een k3d-cluster aanmaken waarvan de doorgestuurde poort overeenkomt met de nodePort uit het manifest;

  • uitleggen waarom de gegevens van een pod verdwijnen zodra je die pod verwijdert;

  • een manifest met meerdere objecten opsplitsen in aparte bestanden;

  • uitleggen waarom pods elkaar via een Service aanspreken en niet via hun IP-adres;

  • een pod vervangen door een Deployment en het verschil tussen beide uitleggen;

  • het aantal kopieën van een Deployment declaratief en imperatief aanpassen;

  • nagaan of gegevens in het cluster bewaard blijven nadat je pods verwijdert en opnieuw aanmaakt.

12.2 Inleiding¶

In dit hoofdstuk zetten we een bestaande Podman-pod stap voor stap om naar een Kubernetes-manifest, met podman kube generate.

We tonen niet alleen hoe je dat bestand genereert, maar ook hoe je het aanpast zodat het werkt in een Kubernetes-cluster, in ons geval k3d.

Onderweg komen de problemen aan bod die bij zo'n omzetting opduiken, en hoe je ze oplost.

Verderop vervangen we de pods ook nog door deployments.

Als casus gebruiken we opnieuw WordPress.

12.3 Podman pods voor WordPress¶

We verwijderen eerst, indien nodig, alle Kubernetes-clusters die nog op de machine staan.

student@virt-k8s-XX:~$ kubectl config get-clusters
student@virt-k8s-XX:~$ k3d cluster delete [naam cluster]

Herhaal het laatste commando hierboven tot er geen clusters meer overblijven. Als je net hoofdstuk 11 hebt afgerond zal je geen Kubernetes-clusters moeten verwijderen.

We installeren WordPress nu eerst als Podman-pod, zoals in het hoofdstuk over pods. Voor de uitleg bij die commando's verwijzen we naar dat hoofdstuk.

student@virt-k8s-XX:~$ podman pod create --name wp-pod -p 8080:80
student@virt-k8s-XX:~$ podman run -d --restart=always --pod=wp-pod -e MYSQL_ROOT_PASSWORD="dbpass" -e MYSQL_DATABASE="wp" -e MYSQL_USER="wordpress" -e MYSQL_PASSWORD="wppass" --name=wp-db docker.io/library/mariadb
student@virt-k8s-XX:~$ podman run -d --restart=always --pod=wp-pod -e WORDPRESS_DB_NAME="wp" -e WORDPRESS_DB_USER="wordpress" -e WORDPRESS_DB_PASSWORD="wppass" -e WORDPRESS_DB_HOST="127.0.0.1" --name wp-web docker.io/library/wordpress
student@virt-k8s-XX:~$ podman ps -a --pod
…

12.4 Genereren van een Kubernetes-manifest¶

We zetten die Podman-pod nu automatisch om naar een Kubernetes-manifest.

student@virt-k8s-XX:~$ podman kube generate -s wp-pod > wordpress.yaml

De optie -s zorgt ervoor dat er naast de pod ook een Service in het bestand komt. Zonder die optie krijg je enkel de pod en moet je de Service zelf schrijven.

We bekijken de inhoud van dat bestand.

student@virt-k8s-XX:~$ code wordpress.yaml

  name: wp-pod
spec:
  ports:

    nodePort: 32723
    port: 80
    targetPort: 80
  selector:
    app: wp-pod
  type: NodePort

Bekijk je die uitvoer, dan zie je wat Podman beschreven heeft:

  • Service met de naam wp-pod

  • Pod met de naam wp-pod

    • Container met de naam wp-db

    • Container met de naam wp-web

    • twee stukken opslag, die Podman zelf heeft aangemaakt omdat de images mariadb en wordpress daarom vragen.

12.5 Toepassen van manifestbestand¶

We verwijderen eerst de Podman-pod met zijn containers.

student@virt-k8s-XX:~$ podman pod rm wp-pod -f
d2402d6d61aad6720c457526f05cbbcb8c29b8aad448c40d838b70fd673a148d
student@virt-k8s-XX:~$ podman ps --pod
CONTAINER ID  IMAGE       COMMAND     CREATED     STATUS …

De pod is daarmee verdwenen.

We maken nu een cluster aan met de onderstaande instellingen.

Let op: de nodePort in het Service-manifest, hier 32723, moet overeenkomen met de poort die je in het k3d-cluster doorstuurt met de optie -p (8080:32723@server:0). Verkeer op poort 8080 van je machine komt dan uit op poort 32723 van de service. Podman kiest bij het genereren een willekeurig nummer, dus kijk eerst na wat er in jouw bestand staat.

student@virt-k8s-XX:~$ code wordpress.yaml

…

…

In het vorige hoofdstuk maakten we een service bereikbaar met kubectl port-forward. Hier pakken we het anders aan: we laten k3d de poort al doorsturen bij het aanmaken van het cluster, zodat die port-forward niet meer nodig is.

student@virt-k8s-XX:~$ k3d cluster create mijncluster --servers 1 --agents 1 -p "8080:32723@server:0"
…

We passen het manifest nu toe.

student@virt-k8s-XX:~$ kubectl apply -f wordpress.yaml
service/wp-pod created
The Pod "wp-pod" is invalid:
* spec.volumes[0].name: Invalid value: "7444f02eb2c3cf9c44f3492cd31112337157101a690dffbf9de2a1fecbb28f4e-pvc": must be no more than 63 characters

* spec.containers[0].volumeMounts[0].name: Not found: "7444f02eb2c3cf9c44f3492cd31112337157101a690dffbf9de2a1fecbb28f4e-pvc"

Het werkt dus niet meteen.

12.6 Back-up maken en manifestbestand aanpassen¶

Maak eerst een kopie van het oorspronkelijke manifest, want we gaan er heel wat in wijzigen.

student@virt-k8s-XX:~$ cp wordpress.yaml wordpress.yaml~

Een tilde achter een bestandsnaam wijst er in Linux meestal op dat het om een reservekopie gaat.

We passen het manifest nu aan zodat het wel werkt.

Een aantal regels mag je zonder meer weglaten: creationTimestamp, de annotaties met io.kubernetes.cri-o.SandboxID en de commentaarregels die met # beginnen. Daarmee is het probleem nog niet opgelost, maar het bestand wordt er een stuk leesbaarder van.

Verwijder dus de volgende regels:

# Save the output of this file and use kubectl create -f to import
# it into Kubernetes.
#
# Created with podman-5.8.2
  creationTimestamp: "2026-11-06T11:22:47Z"
  annotations:
    io.kubernetes.cri-o.SandboxID/wp-db: b662df54310f7b997504d35b28d6c5a9b5f5ba69c60bfc07483b1de9805824ae
    io.kubernetes.cri-o.SandboxID/wp-web: b662df54310f7b997504d35b28d6c5a9b5f5ba69c60bfc07483b1de9805824ae
  creationTimestamp: "2026-11-06T11:22:47Z"

De twee lange namen horen bij opslag die Podman zelf heeft aangemaakt: de images mariadb en wordpress vragen daarom. In dit hoofdstuk werken we zonder opslag, net als in het vorige, en daarom halen we die stukken uit het manifest. Daarmee verdwijnt ook de foutmelding, want dan staan die namen er niet meer in.

Verwijder bij allebei de containers het blok volumeMounts met de twee regels eronder, en verwijder onderaan het volledige blok volumes.

    volumeMounts:
    - mountPath: /var/lib/mysql
      name: 7444f02eb2c3cf9c44f3492cd31112337157101a690dffbf9de2a1fecbb28f4e-pvc
    volumeMounts:
    - mountPath: /var/www/html
      name: dbd96b4a04f6ab9bc81e8d54530b5a68c21e9d249f5729fb98f79eba19c06894-pvc
  volumes:
  - name: 7444f02eb2c3cf9c44f3492cd31112337157101a690dffbf9de2a1fecbb28f4e-pvc
    persistentVolumeClaim:
      claimName: 7444f02eb2c3cf9c44f3492cd31112337157101a690dffbf9de2a1fecbb28f4e
  - name: dbd96b4a04f6ab9bc81e8d54530b5a68c21e9d249f5729fb98f79eba19c06894-pvc
    persistentVolumeClaim:
      claimName: dbd96b4a04f6ab9bc81e8d54530b5a68c21e9d249f5729fb98f79eba19c06894

Kijk je het bestand grondig na, dan valt er een fout op.

    …
    name: wp-db
    ports:
    - containerPort: 80
    …

De databaseserver luistert op poort 3306 en niet op poort 80.

Let wel: een containerPort in een manifest opent niets. Het is documentatie, bedoeld voor wie het bestand leest; het verkeer loopt via de targetPort van de Service. Een verkeerde waarde zorgt dus niet voor een storing, maar ze staat er wel verkeerd.

We passen het manifest dan ook aan.

    …
    name: wp-db
    ports:
    - containerPort: 3306
    …

Bij de container wp-web staat dan weer geen poort. Voeg die regels daar toe, onder name: wp-web.

…
    ports:
    - containerPort: 80
…

12.8 Instellen WordPress¶

Op een andere computer in het netwerk 192.168.112.10 kan je nu het volgende doen.

12.9 De pod verwijderen en opnieuw aanmaken¶

We vragen eerst de service en de pods op.

student@virt-k8s-XX:~$ kubectl get service
NAME         TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
kubernetes   ClusterIP   10.43.0.1       <none>        443/TCP        104m
wp-pod       NodePort    10.43.199.246   <none>        80:32723/TCP   104m

De service kubernetes heb je niet zelf gemaakt: die bestaat in elk cluster en verwijst naar de API-server.

student@virt-k8s-XX:~$ kubectl get pods
NAME     READY   STATUS    RESTARTS   AGE
wp-pod   2/2     Running   0          83m

Er staat 2/2 omdat wp-pod uit twee containers bestaat.

We verwijderen nu de service en de pod, en maken ze daarna opnieuw aan.

student@virt-k8s-XX:~$ kubectl delete service wp-pod
service "wp-pod" deleted from default namespace
student@virt-k8s-XX:~$ kubectl delete pod wp-pod
pod "wp-pod" deleted from default namespace

De website is daarmee niet meer bereikbaar.

We maken de service en de pod opnieuw aan met het manifest.

student@virt-k8s-XX:~$ kubectl apply -f wordpress.yaml
service/wp-pod created
pod/wp-pod created

De website is er weer, maar WordPress vraagt opnieuw om ingesteld te worden. De database en de bestanden van de website zaten in de containers van de pod, en die zijn mee verdwenen. Een pod bewaart dus niets. Wil je dat gegevens een pod overleven, dan koppel je er opslag aan met een PersistentVolumeClaim; dat laten we hier buiten beschouwing.
